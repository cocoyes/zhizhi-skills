# 输出深度评估与调整

评估日期：2026-11-06。范围为本仓库 10 个生活 Skill；相邻 runtime 与 zhizhi-go 只读检查，不修改服务、线上提示、数据库或模型配置。

## 结论与证据边界

旧版没有硬性字数上限，也没有证据证明它必然短答。一次独立定性试答中，明确要求“完整攻略”和“完整计划”时，旧版已经能生成分日/分周安排、预算/时间表、备选及第一步；一句感谢也保持短句。因此这次不能声称复现并修好了“所有复杂任务输出过短”。

可以直接从指令确认的风险是：计划的默认深度和每个栏目应展开到什么粒度不够明确。用户常见的“帮我安排”既可能被理解为提纲，也可能得到完整方案，缺少稳定的完成标准。

| 旧版信号 | 可能影响 | 本次调整 |
|---|---|---|
| 10 个 Skill 共用“必要的步骤”“简单问题几句话”“复杂计划才分节” | 没有清楚界定普通计划需要多少执行信息 | 区分单点回答、常规方案、完整方案；计划类默认可直接执行 |
| 领域方法写了需要考虑什么，输出段常只有一句栏目概述 | 考虑过某因素，不等于真的向用户交付了该信息 | 每领域明确数量、步骤、解释、条件与备选的粒度 |
| 旅行示例是处理概要；多数其他示例是短任务 | 短示例可能成为复杂任务的输出锚点 | 增加旅行、饮食、学习的展开示例，保留短问示例并明确适用范围 |
| “少量变化”“一个推荐”“低精力保底”是合理的用户体验约束 | 可能误用为减少解释，而非减少用户任务 | 明确行动可以少，选中的行动仍需讲清；保底不替代正常方案 |

以上“可能影响”为提示词层面的判断，不是线上模型短答率或因果实验结果。

这些来源没有提供适用于知枝十个生活领域的统一字数标准。固定“每次至少两千字”既无依据，也会损害短问、倾诉、游戏及即时安全场景，所以没有采用。

## 采用的深度规则

1. 单点问题直接交付结论或操作；用户指定简版、一句话或局部修改时遵守范围。
2. 普通“帮我安排”默认交付能执行的方案：理由、假设、安排、数量/时间/费用和调整方法。
3. 完整请求及多日、多阶段、多约束任务先总览再展开，覆盖全部日期或阶段；说明资源、取舍、备选与检查条件。
4. 以完成度决定篇幅，无统一最低字数或上限。扩展具体内容，不重复口号，也不以“需要我再详细写吗”结束一个尚未完成的请求。

每份 Skill 保留自身的 Markdown、工具真实性和领域边界约束，不新增输出协议、子 Skill 路由、资源读取或脚本运行依赖。名称和 description 不变，避免为修改篇幅无谓改变路由。

## 宿主链路的影响

本地只读源码检查发现：

- `zhizhi-agent-runtime/skill.go` 的 `skillExecutor.Execute` 将宿主 system prompt 与选中 Skill 正文、task 一起交给子执行；结束后把 `result.Text` 放入工具结果。该文件和 `api/agent/internal/agent/skills/provider.go` 未见 Skill 专属的字符/篇幅截断配置。
- `zhizhi-go/docs/promot/chat-agent-execution.md` 及同源 SQL `script/sql/agent/runtime_v1_1_1_skill_prompt.sql` 仍有“回复自然、简洁”。这是比 Skill 正文更高优先级的宿主提示，可能继续影响子执行风格。
- `api/agent/internal/responsecomposer/composer.go` 会加载 `chat.response`，把执行结果作为 `execution_facts` 再生成最终回复。子结果详细不代表最终回复保留全部细节。
- `api/agent/internal/aimodel/factory.go` 会传递配置中的 `MaxTokens`，对部分模型使用 `max_completion_tokens`。本次未读取运行中的模型配置，不知道线上实际额度，不能排除模型限制导致截断。

因此，本次修改改善 Skill 提供的交付规范，不能单靠 Skill 越过宿主规则或模型额度。接入时建议在委派 task 中保留用户要求的深度、期限、预算与已有方案；主回复应保留可执行安排、关键数字、假设和备选，主要删去内部过程与重复话语。如果仍然短，分别检查子执行 `text` 和最终聊天回复，先定位在哪个阶段丢失内容，再调整该阶段的提示或额度。

这些是接入检查建议，本次没有执行任何提示 SQL、更新 Redis、启动服务或更改线上数据。验证范围见 [验证记录](verification.md)。
